Shared email drafts: proposed data design

Baseline: eb66ca2556419cf46942f507196b26418821cb22. Approved amended target architecture. Independent technical review PASS; all design approvals complete. No implementation or live migration.

Specification · Architecture · API/MCP comparison

The amended target data contract, including the file-origin field and revised access/replay policies, is approved. Existing metadata comes from repository migrations and queries. No production database was accessed.

Table map

Table / changeOne row representsLifecycle
ticket_drafts · NEWOne draft identity, retained after sending or discarding; at most one active draft per ticket.No automatic expiration. Terminal identities remain with the ticket; physical ticket/workspace deletion cascades. Send/discard clears body, Cc/Bcc and mailbox selection and removes active attachment reservations; keep identity, original hash, attribution and committed message result.
ticket_draft_attachments · NEWOne currently reserved file in one active draft.Remove reservation on removal, discard or committed send. Existing cleanup handles genuinely unattached/unreserved files after its existing threshold.
ticket_preparations · NEWOne durable creation reference in a workspace and caller-chosen namespace.Retain until workspace deletion, including after 24-hour HTTP replay expiry. A NULL ticket result is a tombstone and returns 410; never recreate it automatically.

Draft-origin file lifecycle

Nullable attachments.draft_ticket_id uses a tenant-safe FK to tickets(workspace_id,id). It survives removal/discard independently of active reservations and requires current authenticated origin visibility before generic signatures. Stream these files with private,no-store and no new external redirect. Pre-association storage redirects retain at most their existing five-minute lifetime.

Migration and verification

Three new tables; composite unique keys on tickets and attachments; internal recipient_locked on messages; nullable draft_ticket_id on attachments. No existing payload field is removed or renamed. Existing data stays unchanged and uses default false for the new message flag.

Exclude active reservations from both cleanup selection and final deletion claims. Keep terminal draft identities and preparation references for durable retries. Do not run old purge workers against newly saved drafts.

The down migration refuses populated feature state. See the architecture for staged promotion and forward-fix requirements. No Informix flow is involved.

Exact new-column dictionary: schema-proposal.json. No field in this proposal claims live-database verification.
